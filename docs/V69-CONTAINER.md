# Windows AppContainer 原始套接字实验

这个实验测量一个受限 Windows 进程能否连接本机回显服务。网络能力在创建测试进程时确定。启动器退出后，独立观察进程才发出开始信号，发送端随后尝试连接。这样可以检验启动器退出期间的行为，也能排除启动器替子进程转发请求的解释。

## 复现

需要 Windows、Python 3 和位于 PATH 的 MinGW-w64 GCC。从仓库根目录运行以下命令。

```powershell
python proxy_v6/tests/repro/v69-container/run.py
```

脚本将同一个小型 C 程序编译到随机临时目录。普通测试进程与 AppContainer 测试进程使用同一可执行文件。实验为当前用户建立一个随机命名的临时 AppContainer 配置，授予该标识读取和执行测试文件的权限。启动时传入零项网络能力。子进程检查自己的令牌类型，等待本轮专用信号，然后连接固定的 IPv4 或 IPv6 回环地址。实验未添加回环豁免，防火墙和系统代理均沿用主机原配置。

每组包括普通进程、启动器退出后的受限进程，以及第二次普通进程。三次使用同一接收端和各自独立的随机挑战。TCP 记录已接受的连接数，UDP 记录到达的数据报数；双方核对回显。TCP 建连截止时间为两秒，退出码 72 表示实验自己的计时器到期。10060 为 Winsock 超时，10013 为 Winsock 拒绝访问。运行结束时删除实验创建的 AppContainer 配置与临时目录。

## 本次 Windows 实测

表内三个数依次对应前对照、受限进程和后对照。

| 通道 | 发送端退出码 | 接收端到达次数 | 可以得出的结论 |
| --- | --- | --- | --- |
| IPv4 TCP | 0 / 72 / 0 | 1 / 0 / 1 | PARTIAL。前后对照回显成功。受限进程在观察窗口内未连上接收端。 |
| IPv4 UDP | 0 / 10060 / 0 | 1 / 0 / 1 | PARTIAL。受限期间接收端零收件，发送端等待回包超时。 |
| IPv6 TCP | 10013 / 10013 / 10013 | 0 / 0 / 0 | BLOCKED。普通进程也无法建立正对照。 |
| IPv6 UDP | 10060 / 10060 / 10060 | 0 / 0 / 0 | BLOCKED。三个阶段都没有回包。 |

本轮运行器退出码为 2，配置删除成功且临时目录已移除。运行器要求普通对照可用、隔离进程返回明确的 10013、接收端零到达，才会把该组判为 PASS。只观察到超时时，具体拦截原因仍未知。后续不受限的 Python 进程连接 `::1` 也同样收到 TCP 10013，所以表中的 IPv6 行反映的是主机回环条件，不能用来证明 AppContainer 策略单独生效。

这套实验覆盖单个测试程序的原始回环套接字。普通进程对照说明同一接收端在故障窗口前后可用。公网出口、启动任意桌面应用及其全部子进程、代理链、系统级防火墙规则生效与故障时整机断网，仍需单独验收。[Microsoft AppContainer 隔离模型](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation)

## 可单独使用的离线工作区

[Offline.wsb](../proxy_v6/tests/repro/v69-container/Offline.wsb) 适用于已经安装并获准运行 Windows Sandbox 的测试机。该文件请求从启动起关闭访客网络、剪贴板、麦克风、摄像头、打印机共享及虚拟 GPU，启用受保护客户端模式，省略宿主文件夹映射和登录命令。适用场景是只需要访客内置程序的离线操作。访客内无法按此配置连到固定出口。宿主中原有浏览器和桌面应用仍按各自配置联网。[Microsoft 的 .wsb 配置说明](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file)

**默认先做只读预检**。从仓库根目录运行命令，检查器解析相邻配置的 XML，计算实际文件 SHA-256，并查看 Windows 系统目录中是否存在启动器。添加 `--self-test` 会在内存中测试九个异常输入。

```powershell
python proxy_v6/tests/repro/v69-container/check_offline.py --self-test
```

预检退出码 0 表示静态配置合格且发现启动器；1 表示配置、读取或自检失败；2 表示静态配置合格但未在系统目录中确认启动器。实际启动能力需要另测。当前 Windows 11 家庭版样本的静态检查通过，九个异常输入全部被拒，退出码 2。访客启动及运行期间的网络实测为 **NOT_TESTED**。

**获准实机验收时**，在具备 Sandbox 的测试机上双击上述 `Offline.wsb`。开始菜单中的默认 Sandbox 使用另一套网络配置。只在新出现的访客窗口中运行测试：查看访客网络接口与默认路由，再让中性测试客户端向自有接收端发送本轮唯一标记。与宿主同时可达该接收端的正对照一起记录。分别验证 IPv4、IPv6、TCP、UDP；接收端不可观测或正对照失败的项目保留未验证。关闭访客并确认丢弃后，访客中的临时工作将被清除。回退方式是结束此访客会话并保留宿主原有工作环境。此配置不提供宿主应用故障时的自动切换。
