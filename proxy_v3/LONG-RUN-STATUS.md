## 4. 24h / 72h 的正确跑法

```powershell
# 24 小时（建议先跑）
python D:\claude防封\proxy_v3\tools\monitor-longrun.py --hours 24 --interval 60 --retry 2 --out D:\claude防封\proxy_v3\evidence\soak-24h.jsonl

# 72 小时扩展
python D:\claude防封\proxy_v3\tools\monitor-longrun.py --hours 72 --interval 120 --retry 2 --out D:\claude防封\proxy_v3\evidence\soak-72h.jsonl
```

要求与实现要点：

| 任务书要求 | 实现 |
|---|---|
| 首试成功率单独统计 | `firstAttemptSuccess` 字段，只统计 `attempt=1` |
| 不以重试后成功率代替首试 | 两者分别输出，且 `retriesUsed` 显式记录 |
| 不删除失败样本 | JSONL 追加写，聚合时全量读取 |
| 连续失败长度 | `maxConsecutiveFirstFailures` |
| 故障时间分布 | `hourly` 桶：每小时样本数与失败数 |
| 分段延迟指标 | 逐样本 `ms`；聚合 p50/p90/p95/p99 |
| 未完成即 PENDING | 覆盖时长 < 设定时长 × 0.98 → 输出 `PENDING` 并返回 7 |
| 可续跑 | 重启后向同一 JSONL 追加，聚合时合并 |

**尚未实现的维度（如实标注）**：
- SOCKS5 握手与 TLS 握手未在长稳工具里**分段**记录（`benchmark.py` 有分段，但那是短测）；
- 未包含"断网后恢复"的自动化编排（需人工断网或 privileged 操作）；
- 未包含固定并发压力测试（当前串行）。

## 5. 判定规则（提前写死，避免事后改口径）

一次 24h 运行只有在同时满足下列条件时才计为 PASS：

1. 实际覆盖时长 ≥ 23.52 h（98%）；
2. `firstAttemptSuccess` ≥ 99.0%；
3. 首试失败样本全部可在 JSONL 中定位（不删样本）；
4. 连续首试失败长度有记录，且最坏值不隐藏；
5. 结束时工具返回 0。

任一不满足即 **FAIL / PENDING**，不得人工调整统计方法。

## 6. 已知残余风险（与长稳相关）

1. **第一跳单点依赖**：StarSky 一旦重启，链路立刻不可用。V1 曾真实发生（`sidecar_latest.log` 01:40:16 记录 `127.0.0.1:11119 … actively refused it`）。`resilient` 档会回落 DIRECT，出口随之改变——长稳期间若出现成片失败，先查 StarSky 进程是否有重启。
2. **UDP 不在静态 IP 上**：长稳工具只测 TCP/HTTPS，因此它的成功率**不代表** UDP 类应用（QUIC/WebRTC/语音）的可用性。
3. **延迟波动大**：本次冒烟中 p90 达 5554 ms（p50 2669），说明存在明显的长尾。24h 数据必须看 p99 与逐小时分布，不能只看平均值。
4. **样本自相关**：即使跑满 24h，60 s 间隔仍会造成时间自相关；结论应表述为"该时段内可用性"，而非"全年可靠"。
