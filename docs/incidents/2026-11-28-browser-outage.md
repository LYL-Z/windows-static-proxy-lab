# 事故记录：浏览器全面打不开（2026-11-28）

> 状态：**已恢复**。系统代理 `127.0.0.1:7897`，静态 IP 出口 `72.245.197.103`。
> 本文只记录现场事实与可复现判据，不含任何凭据。

## 1. 一句话结论

StarSky 核心在 **02:30:19 重启**，链式代理的第一跳断开；Clash 无法拨通上游时会**直接关闭客户端连接**，
于是所有走系统代理的程序（Chrome/Edge）表现为"所有网站都打不开"；
而 QQ、豆包这类**不走系统代理、走 TUN** 的程序完全不受影响——这就是"两个软件都显示正常，但浏览器全挂"的原因。

## 2. 症状与看似矛盾的现象

| 观察 | 实际含义 |
|---|---|
| Chrome：`ERR_CONNECTION_CLOSED` | 代理已接受连接、随后被关闭 = 上游拨号失败 |
| Clash Verge 界面"正常"，有 48 条活跃连接 | UI 展示的是自身运行状态，不代表能否拨通上游 |
| StarSky "加速中"，自带诊断"正常" | 它只验证自己的隧道，不知道 Clash 在用它当第一跳 |
| QQ / 豆包正常 | 不经过 WinINET 系统代理，走 TUN |
| `ip.net.coffee` 打不开 | 站点侧关闭连接；同一时刻 `curl` 经 7897 返回 **200**，与本次故障无关 |

## 3. 关键时间线（本机时钟）

| 时间 | 事件 |
|---|---|
| 00:55:04 / 00:55:06 | `clash-verge` / `verge-mihomo` 启动 |
| **02:30:19** | **`magicspeed`（StarSky 核心）重启** ← 故障触发点 |
| 之后 | 浏览器全部 `ERR_CONNECTION_CLOSED`；QQ/豆包正常 |

## 4. 诊断证据（只读）

```text
# 两个本地代理都在监听，所以"端口没开"不是原因

# 系统代理指向 Clash

# 链路的真实出口（故障恢复后）——这就是唯一可信判据
curl -x http://127.0.0.1:7897 https://api.ipify.org   -> 72.245.197.103
curl -x http://127.0.0.1:11119 https://api.ipify.org  -> 107.149.115.70   (StarSky 节点，非固定)

# 运行配置已不是 V4 生成（rules 变为 GEOIP,CN,DIRECT + MATCH,PROXY，marker 丢失）
rules: - GEOIP,CN,DIRECT / - MATCH,PROXY
```

## 5. 修复动作

1. 把系统代理从 `7897` 临时切到 `11119`（StarSky）验证浏览可用 —— 确认是"链断了"，不是"网卡坏了"；
2. 确认 `7897` 恢复后切回 `7897`；
3. 刷新浏览器（系统代理变更后，浏览器里已建立的旧连接需要重开）。

## 6. 三个"假故障"，不要误判

| 报错 | 真相 |
|---|---|
| `CRYPT_E_REVOCATION_OFFLINE (0x80092013)` | Windows Schannel 的**证书吊销检查**连不上，本地密码学栈问题；Chrome 不走这条路径 |
| `qq.com` 返回 `501` | 服务器对 `curl` 默认 UA 的正常拒绝，不是代理错误 |
| `github` 18s 超时 | 实际已传输 **527 KB**，是**慢**不是**断** |

**唯一判据**：`curl -x http://127.0.0.1:7897 https://api.ipify.org` 是否返回 `72.245.197.103`。

## 7. 根因与设计缺口

- **直接原因**：StarSky 核心重启 → 第一跳 11119 短暂不可用 → 链式代理断裂。
- **放大原因**：当前策略组为**失败关闭**（`select`，不含 `DIRECT`），且规则为 `MATCH,PROXY`，
  所以上游一断，**所有非 CN 流量立刻失败**，浏览器并发几十条连接 → 体感"全网瘫痪"。
- **缺失能力**：链路断开后**没有自动恢复**，也没有在系统层给出可见告警；UI 反而显示"正常"。

## 8. 遗留问题

1. `proxy_v4/state-v4.ps1` 当前报 `$integrity` 未赋值，并输出 `STATE FAILED / chainStatus NO_EXIT`，
   而同一时刻 `curl` 能拿到静态 IP —— **状态机误报**，比故障本身更危险，应优先修。
2. 缺少"第一跳重启 → 自动重连/告警"的守护机制；每次 StarSky 换节点或重启都需人工介入。

## 9. 可选缓解（需用户批准，未执行）

- 给 StarSky 的第一跳加**只读**健康探测（例如每 30s 测一次 `CONNECT`），异常时弹通知；
- 或改用 `resilient` 策略组（含 `DIRECT`），代价是断链时会**静默改出口**，与"固定出口"目标冲突；
- 或让 StarSky 不写系统代理（TUN 模式通常可不写），从根本上消除三方争抢。
